# TCP 头部组成
## 疑问
1. 源端口号和目的端口号它们16bit是不包含ip地址的吗？只包含端口号吗？是在ip头部才有吗？
回答：不包含。TCP头部的16bit端口字段只包含端口号，不包含IP地址。IP地址在IP头部里面。
2. 这个接受窗口意思是数据包的数目，还是说一个数据包的大小
TCP接收窗口表示接收方还能接收多少“字节”的数据。

**TCP不是按字符编号，而是按字节编号。**

|          | hello  | 大数据               |
| -------- | ------ | ----------------- |
| 数据大小     | 5 Byte | 10000 Byte        |
| 是否超过MSS  | 否      | 是                 |
| TCP段数量   | 1个     | 多个                |
| Seq变化    | 1001   | 1001、2461、3921... |
| ACK方式    | 一次确认   | 累计确认              |
| 是否需要窗口控制 | 基本无感   | 明显影响              |

## 传输 5 Byte

```mermaid
sequenceDiagram
    participant A as Sender A
    participant B as Receiver B

    A->>B: TCP Segment<br/>Seq=1001<br/>Data=hello(5 Byte)

    Note over B: 收到数据<br/>h=1001<br/>e=1002<br/>l=1003<br/>l=1004<br/>o=1005

    B->>A: ACK=1006<br/>Window=8000

    Note over A: 确认成功<br/>继续发送后续数据
```

虽然是多个但是只给最后的ACK，不存在中间的ACK=1004 因为是整包的

## 传输 5000 Byte MSS 1460 Byte
```mermaid
sequenceDiagram
    participant A as Sender A
    participant B as Receiver B

    Note over A: 应用数据5000 Byte<br/>MSS=1460<br/>需要拆分

    A->>B: Segment 1<br/>Seq=1001<br/>Data=1460 Byte

    A->>B: Segment 2<br/>Seq=2461<br/>Data=1460 Byte

    A->>B: Segment 3<br/>Seq=3921<br/>Data=1460 Byte

    A->>B: Segment 4<br/>Seq=5381<br/>Data=620 Byte


    Note over B: TCP按Seq排序<br/>重新组装字节流

    B->>A: ACK=6001<br/>Window=8000
```

超过 MSS，拆开成多段，存在后段先到可能。比如 Segment 3 4 先到，会重新发送ACK = 1001

## 新理解
两个重复ACK只能说明“前面的某个数据没有连续到达”，无法定位；三个重复ACK时，TCP推断最前面的未确认Segment丢失，并触发快速重传。

比如收到了Segment34，发送了两个 ACK 1001，对于客户端来说，实际上有可能是Segment 1&3丢失，也可能是Segment 1&4 丢失；只有收到了三个 ACK 1001，才一定是Segment 1丢失。（时间足够久，不考虑Segment 1特别慢的特殊情况）

## TCP 3次握手 & 4次挥手
```mermaid
sequenceDiagram
    participant C as 客户端 Client
    participant S as 服务器 Server

    %% TCP 三次握手
    rect rgb(240,240,255)
    Note over C,S: TCP 三次握手（建立连接）

    C->>S: ① SYN=1<br/>seq=x<br/>请求建立连接

    S->>C: ② SYN=1 ACK=1<br/>seq=y<br/>ack=x+1<br/>同意连接

    C->>S: ③ ACK=1<br/>seq=x+1<br/>ack=y+1<br/>确认收到SYN+ACK

    Note over C,S: 连接建立 ESTABLISHED
    end


    %% 数据传输
    rect rgb(240,255,240)
    Note over C,S: TCP 数据传输

    C->>S: HTTP Request<br/>seq=x+1
    S->>C: ACK<br/>确认收到数据

    S->>C: HTTP Response<br/>seq=y+1
    C->>S: ACK<br/>确认收到数据

    end


    %% TCP 四次挥手
    rect rgb(255,240,240)
    Note over C,S: TCP 四次挥手（断开连接）

    C->>S: ① FIN=1<br/>seq=u<br/>客户端请求关闭连接

    S->>C: ② ACK=1<br/>ack=u+1<br/>确认收到FIN

    Note over S: 服务器可能还有数据未发送

    S->>C: ③ FIN=1 ACK=1<br/>seq=v<br/>服务器发送关闭请求

    C->>S: ④ ACK=1<br/>ack=v+1<br/>确认收到FIN

    Note over C,S: 连接关闭 CLOSED
    end
```
问题：为什么不是2次握手或者4次握手呢？
回答：2次握手的话，如果有延迟的 SYN 请求建立连接，服务器可能凭空打开连接浪费资源。4次握手是不必要的，无论这个第三次的ACK是否丢失，如果没有收到ACK，并且也没有后续数据传来，服务器会重发SYN=1 ACK；如果没有收到了ACK，但有后续数据传来，连接直接建立了。

问题：为什么不是3次挥手呢？
回答：TCP连接是双工连接，如果一边发了FIN，没有收到FIN对应的ACK，会保持连接不断，占用资源。
